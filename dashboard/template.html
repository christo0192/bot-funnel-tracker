How to read this console

This section explains every number on the console: what it means in business terms, the exact rule behind it, and the BigQuery columns it comes from. It describes the logic of today's build (dashboard/template.html and pipeline/build_data.py). It quotes no figures, because every number changes with each daily refresh.

Three ideas answer most questions. (1) A "lead" is one email address at its newest MasterClass registration, and every panel picks leads by that registration's lead date. (2) Most counts are "ever, up to the latest refresh": a call, answer, status or sale made after the selected range still counts for that range's leads. Only a few HubSpot-driven figures are cut off at the range end (§2). (3) Percentages do not all share the same base, so §2 lists the base of every one.

1 · Data sources & refresh

The page is static. A pipeline reads BigQuery, computes every figure, writes data.json and bakes it into this page. It runs every day at about 10:00 IST and again at about 13:00 IST (see Daily refresh below). Nothing queries BigQuery while you browse, so the numbers only change at the next refresh. The chain: view ik-marketing-data.India_Leads.Bot_Calling_Phase2_leadwise → pipeline/build_data.py → main() (two BigQuery queries: one scan of the view with a Contacts subquery LEFT JOINed in for the corrected RTE date, and one Contacts query for the status history of the VC-booked leads) → data.json → pipeline/inject.py (fills the data placeholder in the botdata script block of dashboard/template.html, escaping every < in the data, and writes site/index.html plus a copy at dashboard/console.html) → Vercel (deploys site/).

One lead (one row of the view) One email address at its newest MasterClass registration, inside a rolling window of roughly the last three to four months. Older registrations of the same email are dropped, and a re-registration moves the lead to its newer date. Daily refresh The console is rebuilt twice a day, at about 10:00 IST and again at about 13:00 IST. Between refreshes the numbers do not change. GitHub Actions workflow "Refresh IK Bot Console" (.github/workflows/refresh.yml).
• Primary trigger: 10:00 IST. An external cron service (cron-job.org) calls the workflow via workflow_dispatch. This comes from the workflow's comments; the trigger itself lives outside the repo.
• Second run: 13:00 IST. GitHub schedule cron: "30 7 * * *" (07:30 UTC). The comments call it a fallback, but nothing checks whether the 10:00 run happened, so it runs every day and rebuilds the page a second time (the "updated" pill then shows the later time). GitHub starts scheduled runs on a best-effort basis, often some minutes late.
Runs share concurrency group refresh, so they never overlap. Steps: python pipeline/build_data.py --out data.json → python pipeline/inject.py → vercel deploy --prod. Each run rebuilds the whole window from scratch. If a step fails, the deploy step does not run and the previous version stays live. Time zones (IST conversion) Which clock each date follows. • Bot call times: DATETIME(TIMESTAMP(webinar_last_call_date),'Asia/Kolkata'), so the bot dates are IST.
• PA call times: DATETIME(timestamp,'Asia/Kolkata'), also IST.
• Contacts: row_added_at is UTC. build_data.py adds +5:30 for VC Done / VC attempted, which therefore use IST. The view's DATE(row_added_at) dates (dcd_moved_date, rte_moved_date, vc_done_date) and rte_moved_date_fixed are UTC calendar dates.
• VC slot date: DATE(SAFE_CAST(verified_slot AS TIMESTAMP)), a UTC date.
• Lead creation time: L10X Lead_created_time, which the view treats as IST (lead_created_ist). L10X is not consistent about this: its incident_leads CTE adds 330 minutes to the same source column to get IST, as if it were UTC. The console does not check which is right; if it is UTC, the "after this registration" cut-off for bot and PA calls is 5½ hours too early.
• Labels: the browser turns day numbers (UTC midnights) into date labels in the viewer's local time zone. Viewers in India see the right dates, but a viewer west of UTC (for example in the Americas) sees every label one day early. The date pickers and the CSV export use UTC dates and are not affected. The header note "One denominator — every headline percentage is a share of Leads" is not true for every tile. The owner has chosen to leave the note unchanged; use the list below for each tile's real base. In a sub-line, "Leads" means Total leads in the selected range.

Base of every KPI tile percentage

  • Total leads: no percentage.
  • Attempted: Attempted ÷ Total leads ("of leads").
  • Connected: Connected ÷ Total leads.
  • Connected · 0 answer: ÷ Connected ("of connected").
  • Connected · ≥1 answer: ÷ Connected.
  • Failed / Never connected: ÷ Total leads.
  • Bot qualified: ÷ Connected · ≥1 answer.
  • Bot disqualified: ÷ Connected · ≥1 answer.
  • VC booked: ÷ Bot qualified ("of qualified").
  • VC Done (Bot Leads): ÷ VC booked. The numerator is gated; the base is not.
  • VC attempted, not done yet: ÷ VC booked.
  • DCD flag: ÷ Total leads.
  • RTE flag: ÷ Total leads.
  • Sale: bot-funnel sales ÷ Total leads.

Percentages show one decimal place. When a tile's base is 0 its sub-line shows "–"; tiles based on Total leads show 0.0% instead.

Other percentages on the page

  • Disqualification reasons: the header % is ÷ Total leads. Each bar's % is ÷ the sum of the bars shown.
  • Qualified — what happens next: the header % is ÷ Total leads. Each bar's % is ÷ the sum of the bars shown.
  • Qualification drivers: every % is ÷ that segment's leads.
  • Pod-wise / PA-wise: bar widths are ÷ that segment's leads. The averages are ÷ that segment's PA-dialled leads.
  • Time to first connect: ÷ the sum of the bars shown, and that sum includes "Not Connected". Only 'a: 0–5 min' and 'Not Connected' match the pipeline's bucket list, so most connected leads are missing from both the bars and the base (known issue, §10).
  • Trends: Daily connect rate = each day's Connected ÷ that day's leads. Qualification & disqualification rate = each day's Bot qualified (or Bot disqualified) ÷ that day's leads, then averaged with the rates of up to 6 earlier active days in the range (a trailing 7-point mean of daily rates, shorter at the start of the range).
  • Bot Evals:
    • Correct classification = agreed ÷ (agreed + wrongly qualified + wrongly disqualified);
    • verdict bars ÷ leads judged;
    • tag bars ÷ leads with ≥1 recognised tag;
    • outcome bars ÷ the sum of the bars shown.
  • CRM table: ÷ the leads in the table after its filter.
  • KPI sparklines: see §3.
